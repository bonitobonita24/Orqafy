# Review Pre-Scope — on-demand reference (V32.51, deliverable #41)

> On-demand — deliverable #41 (V32.51). Authority: `security.md` §L1-L6.

> **Advisory-only, always exit 0.** `review-scope.mjs` never blocks a review, never blocks a commit, and
> never blocks a build. It is a deterministic pre-pass that hands `/code-review` a starting manifest — a
> guaranteed FLOOR of what to look at, never a ceiling on what the review actually covers.

This is the fleet-standard answer to "what should a code review look at, deterministically, before the
reviewer starts reading diffs." It parses a diff, applies a conservative review-worthiness gate, and
resolves two things per review-worthy file: which `security.md` §L1-L6 lenses are in play, and which
`audit-app.sh` scanner tools are relevant. The output is a manifest — JSON for tooling, Markdown for a
human — written to `test-artifacts/review/`. Companion: `security.md` (L1-L6, the human/AI-reasoning
security layer whose table this tool mirrors), `audit.md` + `audit-app.sh` (the T1/T2 scanner toolkit
this tool's scanner map points into), `phases.md` (Phase 5 validation), the `/code-review` skill (§5,
the primary consumer).

---

## 1. Purpose + the two design laws

`review-scope.mjs` exists to close a specific gap: an ad-hoc code review can silently skip a tenant-scoping
check on a `router.ts` file, or miss that a new `route.ts` handler bypasses tRPC's RBAC middleware entirely.
A deterministic pre-scope pass catches that class of miss mechanically, before the reasoning-driven review
even starts — the same "automated layer beneath the reasoning layer" relationship `audit.md`'s scanners
have to `security.md`.

Two design laws govern everything the tool does. Both are load-bearing — a change to either changes what
"correct" means for this tool.

**DESIGN LAW 1 (FLOOR-not-ceiling).** The manifest lists the MINIMUM guaranteed lenses/scanners per file —
never the full scope of what a reviewer should check. It ADDS to the reviewer's own open-ended judgment; it
never caps or replaces it. A lens absent from the manifest for a given file is NOT permission to skip that
concern — it just means the deterministic pass didn't have a strong-enough signal to guarantee it. The
reviewer reviews beyond the manifest freely, on every file, always.

**DESIGN LAW 2 (conservative gate).** The review-worthiness gate defaults to INCLUDE. It excludes
certain-noise ONLY: lockfiles (`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`), generated build output
(`dist/`, `build/`, `.next/`, `node_modules/`), binary/asset files (images, fonts, sourcemaps), `.snap`
snapshot files, and files whose first few added lines carry a generated-header marker (`@generated`,
`DO NOT EDIT`, `prisma-client`, `Code generated by`). It ALWAYS keeps `.d.ts` files, deletions, tests,
config, docs, and migrations — even though those categories might look skippable, a deletion can remove an
authz check and a config/migration change can be exactly where a security regression hides.

## 2. How to run it

```bash
node scripts/review-scope.mjs [--base <ref>] [--diff <path>]
```

- **No flags** — diffs the working tree (`git diff`, uncommitted changes).
- **`--base <ref>`** — diffs against a ref (e.g. `--base main`, `--base HEAD~3`) via `git diff <ref>`.
- **`--diff <path>`** — reads a pre-computed unified diff from a file instead of shelling out to git
  (useful for CI, or for diffing a PR patch that isn't the current working tree).

The manifest lands at:

- `test-artifacts/review/review-manifest.json` — machine-readable, `schemaVersion` + `generated` timestamp
  + the full per-file lens/scanner breakdown.
- `test-artifacts/review/review-manifest.md` — the same data rendered as a Markdown table, led by the
  FLOOR-not-ceiling banner, for a human (or `/code-review`) to read directly.

Both files are written on every run, and the Markdown table is also echoed to stdout. **The tool always
exits 0.** If the diff can't be read for any reason (bad ref, unreadable path), it falls back to an
empty-diff manifest whose `notice` field explains what happened, still writes both files, and still exits
0 — a broken diff source is never a reason to block a review.

## 3. Manifest reading guide

Read the manifest as a **checklist floor, not a checklist ceiling**. Every entry in `files[]` names:

- **`file`** — the path, from the diff's `b/` side (post-change path; renames land under their new name).
- **`reviewWorthy`** — always `true` for entries in `files[]` (excluded files land in `skipped[]` instead,
  with a `reason`).
- **`lenses`** — the guaranteed-minimum `security.md` §L1-L6 concerns for this file (§4 below).
- **`scanners`** — the guaranteed-minimum `audit-app.sh` tools relevant to this file (§4 below).
- **`reason`** — why the gate included it (`"no exclusion matched — default include"` for the common case,
  or `"deletion — verify no dangling refs/authz removal"` for a deleted file).

**Confidence tags — `content` vs `path`.** Every lens and scanner hit carries a `confidence` field:

- **`content`** — a code pattern in the file's added lines matched the lens/scanner's content regex. This
  is the strong signal: the tool saw something in the actual diff content that looks like the concern in
  question (e.g. a `.findMany(` call inside a file under `server/`/`routers/` → L1 tenant-scoping at
  `content` confidence).
- **`path`** — only the file's location matched (no content regex fired, or the lens has no content rule
  and fires on path alone). This is the weaker-but-still-valid floor: the location alone is enough reason
  to guarantee the reviewer looks, even without a strong content match. Treat a `path`-confidence hit as
  "look here, the file lives where this concern typically lives" rather than "the tool found the exact
  pattern."

**Route-handler force-fire.** Any file matching `app/**/route.ts(x)` or `pages/api/**` unconditionally
gets L1 (tenant-scoping), L3 (rbac), and L4 (rate-limit+transport) added at `path` confidence if not
already present, tagged with `rule: "route-handler-bypass"`. This mirrors `security.md`'s "Route Handlers
bypass tRPC" finding — a Next.js route handler has none of tRPC's middleware chain, so tenant scoping, RBAC,
and rate limiting are never automatically applied there and must be hand-checked every time.

**Deletions** get an empty `lenses`/`scanners` array and a fixed `reason` — a deleted file has no surviving
content to scan, but the deletion itself is still `reviewWorthy: true` because removing a file can remove an
authorization check, a validation guard, or an audit-log call as a side effect.

The `skipped[]` array lists files the gate excluded, each with its `reason` — always one of the
certain-noise categories in Design Law 2 (§1), never a security judgment call.

## 4. Lens signal table + scanner map

**L1-L6 lens map.** Authority for the meaning of each lens: `.ai_prompt/security.md` §L1-L6 — this table
mirrors that authority and does not redefine it.

| Lens | Concern | Fires on path | Fires on content | Route-handler force? |
|---|---|---|---|---|
| **L1** | tenant-scoping | `server/`, `/api/`, `routers?/`, `trpc` | a `db`/`prisma`/`ctx.db` call chained into `findMany`/`findFirst`/`findUnique`/`count` | ✅ forced on `route.ts`/`pages/api` |
| **L2** | input-validation | `route.(t|j)sx?$`, `actions?\.` | `req.json()/formData()/text()`, `NextRequest` | — |
| **L3** | rbac | `middleware.(t|j)s$`, `routers?/`, `guard` | `publicProcedure`, `protectedProcedure`, `router(`, `hasPermission`, `role` | ✅ forced on `route.ts`/`pages/api` |
| **L4** | rate-limit+transport | `route.`, `auth`, `login`, `webhook` | `NextResponse`, `export async function POST/PUT/DELETE/PATCH` | ✅ forced on `route.ts`/`pages/api` |
| **L5** | audit-log | `routers?/`, `server/` | `.create(/.update(/.delete(/.deleteMany(/.updateMany(`, `.mutation(` | — |
| **L6** | prisma-guardrails | `schema.prisma` | `deleteMany`, `updateMany`, `{ id: { in: }` | — |

**Scanner → `audit-app.sh` map.** Authority for what each tool actually does: `.ai_prompt/audit.md` §0-3 +
`scripts/audit-app.sh`. This tool's scanner rules only tell the reviewer WHICH T1/T2 tool is relevant to a
changed file — it does not run the scanner itself.

| Scanner | Tier | Fires on | Fires on content |
|---|---|---|---|
| `gitleaks` | T1 | `.env(.*)?$` | an `api_key`/`secret`/`token`/`password`-shaped assignment |
| `semgrep` | T1 | `.ts/.tsx/.js/.jsx` | — |
| `tsc` | T1 | `.ts/.tsx` | — |
| `eslint` | T1 | `.ts/.tsx/.js/.jsx` | — |
| `trivy` | T2 | `Dockerfile`, `docker-compose.yml` | — |
| `osv` | T2 | `package.json` | — |
| `syft` | T2 | `package.json` | — |
| `backstop` | T2 | `page.tsx` | a JSX `return (` |

A file can carry multiple scanners (e.g. a `.tsx` page file gets `semgrep` + `tsc` + `eslint` + potentially
`backstop`). None of this runs the actual scanner binaries — for that, run `audit-app.sh` per `audit.md`.

## 5. Consumption by `/code-review` (seam A)

The integration seam with the `/code-review` skill is deliberately thin:

1. **Run it FIRST**, before the review itself starts reading diffs: `node scripts/review-scope.mjs
   [--base <ref>]`.
2. **Read the manifest as a guaranteed floor**, not a checklist to tick off and stop. `/code-review`
   should read every `files[]` entry's `lenses`/`scanners` as "these concerns are GUARANTEED in scope for
   this file" — then keep reviewing beyond that, on every file, using its own judgment same as always.
3. **Review beyond it freely.** The manifest never narrows what `/code-review` looks at — it only widens
   the floor of what's guaranteed not to be silently skipped. A file with an empty `lenses`/`scanners` array
   still gets a full review; it just means the deterministic pass found no strong location/content signal
   for it.
4. **Freshness — regenerate if the diff changed.** The manifest is a snapshot of the diff at the moment it
   was generated. If the reviewer amends the diff mid-review (more commits, a rebase, new working-tree
   edits), re-run `review-scope.mjs` before trusting the manifest again — a stale manifest against a moved
   diff is worse than no manifest, because it can silently omit a file that only became part of the diff
   after the manifest was generated.

---

## 6. Advisory-only posture — never gates, never blocks

`review-scope.mjs` has no blocking mode and no gate wiring anywhere in the framework. It always exits 0,
including on a diff-read failure (§2). It is not invoked automatically at any phase, commit hook, or CI
step — it is a tool `/code-review` (or a human) reaches for deliberately, the same manual/on-demand posture
`audit.md`'s toolkit uses by default. Nothing about this tool's output can fail a build, block a commit, or
gate a merge; its only effect is widening what a review looks at.
